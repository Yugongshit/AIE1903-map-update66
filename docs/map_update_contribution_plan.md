# 地图更新模块：可验证的贡献路线

以下是基于 2026-11-13 仓库现状提出的工作方案，**尚未实现这些新算法，也没有把同学的 Planning 接成在线驾驶器**。推荐主线是：**从可信的局部传感器观测生成可执行地图补丁，再用固定规划器证明更新的作用。** 五车交互平台可以提供测试场景；平台本身不能代替地图更新方法的有效性证据。

分工应沿用项目的[感知、M3 可靠性、地图维护与 Planning 接口关系](project_plan.md#我们要完成什么)，不要把整条自动驾驶链都揽到你的模块里：

| 负责方 | 主要交付 |
| --- | --- |
| 感知同学 | 物体/曲线观测、类别、位姿与投影来源、时间戳 |
| M3 同学 | 对齐与关联质量、有效覆盖、观测冲突是否可信及原因 |
| 你的地图模块 | 消费这些结果，形成局部结构补丁、共享边界一致性、状态通行约束、版本执行与验证 |
| Planning 与控制同学 | 动态轨迹预测、路线/行为规划、避让决策与车辆控制 |

下面第一、二项是你的实现主线；第三项是你与 Planning 组合作的评估。共同定位偏差处理属于与 M3 商定后的可选深化，不要求你重做其可靠性模块。

## 先认清现在做到了哪里

现有项目已经区分道路结构与附着状态，有物理边界去重、多帧局部差异判定、状态事件生命周期、修改资格检查、版本和来源校验。这些是有用的基础，后续报告应准确说明自己新增或改进了哪部分。

但地图修改还有一个关键缺口：**能够显示一张更新图，不等于已能从传感器结果自主生成这张图。** 当前仿真中的 Argoverse 道路更新使用已交付的参考变化；自主预测与参考重放在代码中明确分开，见 [pipeline_v2.py](../map_update/pipeline_v2.py#L426)。

以已保存的[检测评估报告](../demo/simulation/validation/detection_metrics.json)为准：

| 评估对象 | 当前结果 | 能说明什么 |
| --- | --- | --- |
| Argoverse 局部边界变化检出 | 340 条可评估物理边界；TP 9、FP 5、FN 22；精确率 64.3%、召回率 29.0%、F1 0.40 | 局部差异能检出一部分变化，仍有误报和漏报 |
| 局部几何偏移准确性 | 14 个预测中 3 个满足 0.5 m 的评价条件 | 检出对象与修正几何正确是两件事，不代表整条道路补丁精度 |
| 自主模型最终结构写入 | 0 项；另有 93 项有效参考对象更新可供对照 | 当前还没有验证自主观测到可执行结构补丁的闭环；93 项不能计作模型检出 |
| nuScenes 状态层 | 23 个状态事件来自已有对象标注足迹；缺少独立变化真值 | 能验证接入和状态处理，不能据此报告真实感知变化准确率 |

局部物理边界与最终参考对象是不同评价单位，两个分母不能混用。当前也没有独立留出场景的准确率。更多测试通过，只能证明程序契约或某些场景行为，并不能自动提升这些算法指标。

nuScenes 的物体类别主要来自官方标注；Argoverse 有上游 YOLOP 的真实推理结果，但本项目复用冻结曲线，没有在本轮重新训练检测器。输入来源见 [Perception 说明](perception_and_composite_map.md#1-nuscenes物体类别沿用官方标注)。

## 第一优先：真正生成局部地图补丁

**研究问题：** 车只看见了一段边界，怎样正确修这一段，同时保持未观察路段、共享边界和车道连接有效？这比继续增加场景按钮更直接对应你的分工。

当前 [write_gate](../map_update/pipeline_v2.py#L24) 明确只检查资格，几何更新按整要素替换处理，共享边界同步编辑还没有实现。[可靠性模块](../map_update/reliability_v2.py#L347) 保存的是一条代表观测曲线，也没有生成多帧融合后的可执行局部补丁。

你可以设计并实现：

1. **带范围的补丁。** 以规范物理边界 ID、原图版本和弧长区间 `[s0, s1]` 表示修改目标。只改变有可靠正观测支持的区间；外部保留原图，并标记为未重新验证的先验。不能拿局部线段覆盖整条道路。
2. **多帧空间融合。** 将观测投影到同一边界弧长，估计横向偏移随位置的变化；联合观测质量、稳健残差、邻域支持、空间平滑和端点连接约束。明确哪些区间可以修改、哪些必须保留，而不只输出一个“有变化”的标签。
3. **共享边界原子更新。** 一条物理边界可能被两条车道反向引用。利用已有 [canonical_boundaries](../map_update/reliability_v2.py#L46) 同步修改全部引用，在临时地图副本检查左右边界交叉、车道正宽度、自交和连接间隙。任一必要检查失败，整组补丁不提交；不能凭几何接近自动增加道路连接关系。
4. **可追溯执行。** 保存观测 ID、时间截止、覆盖区间、前后几何、验证结果及版本哈希，做到原子提交与精确回退。可以复用参考重放的事务机制，但补丁的修改后几何必须来自观测，不能读取参考真值 `current_state` 当作预测。

**基线与消融：** 同样的感知输入下比较“不改图”“单帧整线替换”“多帧拟合”“多帧拟合＋局部覆盖”“再加入共享引用和拓扑检查”。分别去掉端点约束、共享边界同步和观测范围限制，看具体会出现哪些错误。

**主要指标：** 变化检出精确率/召回率、可观测区间的曲线误差、正确修正长度、误写长度、未观察区域被误改长度、共享边界不一致数、车道自交数、连接间隙、首次有效观测到正确提交的延迟。不能只对成功写入的样本计算质量、把失败样本丢掉。

**数据条件：** 带时间戳的城市坐标曲线、传感器来源、投影/位姿质量、候选匹配与观测范围。现有冻结曲线可先支撑开发和受控实验；若要判断实际道路而非漆线是否移动，还需明确观测类型与对应关系。没有完整可见性时，先做有正观测支持的局部位移，不做“没看到所以删除”。

## 第二优先：把状态层转成有范围的地图通行约束

**研究问题：** 路障与车道相交，并不一定意味着整条车道不能通行。你的模块怎样告诉 Planning “具体影响哪一段、剩余多宽、依据是什么、现在是否仍有效”？

**自己的设计部分：** 将上游已关联的占用轮廓映射到车道弧长区间，估计局部剩余宽度，并保留 M3 的质量、覆盖与有效性信息。输出受影响车道、空间范围、车辆尺寸假设及几何限制；不替 Planning 决定如何绕行、预测其他车的未来路线或输出油门转向。几何上剩余空间足够也不等于动态驾驶已经安全。

沿用现有状态身份与生命周期，不把暂时遮挡当成障碍消失，也不把车、人和路障写成永久道路几何。对未知可见性保留未知状态，而不是自行生成 M3 的“已充分观察”结论。

**基线与消融：** 比较“只要相交就整车道封闭”“仅提供原始占用多边形”“局部受影响区间与剩余宽度约束”。再去掉上游不确定性、时间有效性和局部范围，观察是否引入误封路或过早清除。

**主要指标：** 受影响区间与剩余宽度误差、误封路/漏封路比例、错误清除率、状态过期后仍被当成确定事实的比例。几何约束是否有用再由第三项固定 Planning 对照检验。

**数据条件：** 车道几何、带时间戳的障碍轮廓、稳定实例 ID、M3 可靠性/覆盖输出，以及独立的占用范围与状态恢复标注。现有 nuScenes 标注可用于验证几何和接口，不能用同一标注既生成输入又声称检测准确。

### 与 M3 协作的可选深化：分清地图真变与定位、投影偏差

**研究问题：** 如果车辆定位偏了 0.8 m，许多道路观测会一起偏移；这与只有一段边界真正改变应如何区分？“以传感器为准”需要处理传感器和坐标误差，不能直接把每帧输出当真值。

现有方法使用固定锚点、多帧中位数、MAD 和时间分块，见 [reliability_v2.py](../map_update/reliability_v2.py#L215)。它能抑制孤立坏帧，但仍把物理对齐标为未验证；稳定的系统性偏差也可能通过多帧一致性检查。

**建议分工：** 由 M3 同学牵头评估多要素共同位姿偏差、关联歧义和跨相机不一致。你的模块重点定义怎样消费其质量、覆盖、坐标偏差范围与拒绝原因：哪些补丁可执行、哪些区间保留先验，以及错误输入是否会造成地图误写。只有双方明确划分了新增工作后，再共同实现偏差估计；不另起一套重复可靠性系统。估计时不能用同一条待判变化边界既校正位姿又证明其未变，稳定锚点不足时不能强行校正。

**基线与消融：** 与当前固定阈值＋多帧稳健统计比较；依次去掉共同偏差处理、时间去相关、多要素关联检查。构造并单独标记“仅位姿偏差”“仅真实局部变化”“两者同时存在”“遮挡/漏检”实验。合成扰动用于检验机制，真实留出场景用于检验推广，两类结果分别报告。

**主要指标：** 固定召回水平下的误报/误写率、位姿偏差估计误差、正确关联率、局部补丁误差和决策延迟。当前质量分不是校准概率；若以后称为“80% 可信”，需要独立校准与可靠性曲线。

**数据条件：** 最好取得上游同学保留的相机标定、位姿/时间同步、原始或投影曲线与模型质量字段，以及若干不同场景。没有这些信息也可先对现有曲线注入已知偏差做机制实验，但不能宣称已解决真实传感器标定误差。

## 第三优先：用固定 Planning 测出地图更新的价值

这里的目标是评价你的地图模块，不承担同学的 Planning 或车辆控制算法。可以与同学约定一个固定版本的规划器，比较它在不同地图输入下的表现。

**实验世界必须固定。** MetaDrive 中真实道路、障碍物、车辆初态和交通控制策略保持同一实验设置；仅改变规划器收到的地图。如果连物理世界也一起换成旧地图，就无法判断更新是否帮助车辆理解同一个真实世界。

| 实验组 | 规划器输入 | 用途 |
| --- | --- | --- |
| A | 原 HD Map | 测旧图的影响 |
| B | 单帧直接覆盖得到的地图 | 体现鲁棒更新是否有必要 |
| C | 你的观测驱动更新图 | 测方法的实际贡献 |
| D | 当前参考真值图 | 只作为评估上限，不进入 C 的推断过程 |

先在相同当前障碍观测下比较道路结构更新；再固定道路图，比较“无状态层”“原始占用层”“你的状态处理层”。这样能分别说明结构补丁和附着状态的作用。五个玩家每次随意开车不适合当主对照实验；应保存其动作序列，或使用固定种子和固定 NPC 策略，在多个种子上重复。闭环中其他车辆对自车的反馈可以不同，但初始化、策略和随机性必须受控并记录。

**主要指标：** 到达率、碰撞率、驶出实际可行驶区域的比例、最小净空、无必要停车、急刹次数、重规划次数、路线长度和任务耗时。报告失败案例与重复次数，不预设你的方法一定改善；路线变短但碰撞更多不能叫总体提升。

现有实时接口已提供六辆车的当前位置、速度、朝向和静态障碍，见 [observation](../map_update/simulation_interactive_server.py#L255)。这些是仿真当前真值，不带传感器遮挡误差，也不包含其他玩家尚未做出的未来动作。示例客户端的 [plan()](../scripts/interactive_planner_client.py#L27) 默认刹车；只有接入同学的真实规划器，并验证“读新观测→重新规划→提交新动作”，才能称为该模块已在线响应其他车。当前接口已通，不能把它说成同学的规划算法已经接好。

## 状态层值得保留的边界

路障、行人和车辆状态应附着在地图或交通世界中，而不是写死成道路几何。项目已实现“有观测则更新、明确完整观察到恢复才清除、缺失/遮挡不当作消失”的[状态生命周期](../map_update/state_events.py#L80)，所以不能再把这个基本概念当作全新成果。

第二项的新增价值在于范围明确、可检验的通行约束，以及错误清除和误封路的评估。实际传感器可见性计算应与感知/M3 分工对齐，需要独立的状态/可见性标注。全场景障碍从第 0 帧显示是离线审阅与仿真先验，评价在线更新时必须按观测时间截断，不能提前使用后面才出现的证据。

## 最小可交付成果

建议先做第一项作为主成果，第二项作为地图状态交付的深化，第三项作为验证方式；先聚焦**已知道路上、观测充分的局部边界几何修改**。M3 可靠性改进是协作可选项，Planning 组继续负责轨迹预测、规划与控制。不要同时承诺建筑重建、新道路发现、交通规则识别、多车博弈和完整动态预测。

交给教授的材料可以集中为四件：

1. 方法说明：输入假设、补丁形式、为什么这样处理观测范围与共享边界，以及明确失败条件。
2. 可复现代码与日志：每次补丁能追到观测，并能还原原图；参考真值在预测冻结后才读取。
3. 基线/消融表：证明每个新增设计解决了哪类问题，而非只有一段好看的演示。
4. 固定规划器对照：同一场景在 A/B/C/D 输入下如何驾驶，性能变化能归因于地图更新。

多帧融合、稳健估计、拓扑约束和状态生命周期都已有研究基础。需要检索相关工作，才能判断具体组合或改进是否构成算法原创。项目价值可以来自明确的问题定义、有针对性的实现、可信的实验设计和可解释的失败分析，不要求从零发明每个公式。现阶段没有原始点云或真实建筑模型，不能把道路外环境复原写成已完成或已具备的数据能力。
