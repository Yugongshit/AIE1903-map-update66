# 持续交通停滞诊断

阶段二。界面时间轴新增服务器状态、最近完成一帧距今秒数、近期仿真/墙钟速度比、运动车辆数、连续停车超过30秒的车辆数及循环等待组数。

- 服务器暂停：不会推进仿真时间，需要房主启动。
- 服务器运行、长时间没有新物理帧：查看引擎忙碌状态、错误与 CPU/渲染耗时。不能从静止截图判断引擎死锁。
- 物理帧持续增加但车辆不动：查看车辆卡片上的停车原因、连续停车秒数、等待对象与路口编号。

车辆速度低于0.3米/秒计作停车诊断。`wait_diagnostic` 按物理实体身份计时，边界新车不会继承旧车的停车历史。队列领车、近场避障对象和路口占用者进入当前等待图；相互可达的等待组标为循环等待。这是排查线索，不是永久死锁的形式证明：对象可能继续移动、失能可能恢复。卡片也区分边界安全入场空位不足、车道姿态跟踪失败、短停和失能。

行人每0.1秒位移小于0.005米计作低速静止。行人调试事件提供 `stationary_for_s`、`waiting_for`、当前阶段和物理受阻改路次数；计划休息也会计入静止时间，必须结合阶段判读，不能把所有静止都算卡住。

## 本轮修复

原规则对路口中心前 `radius + 20m` 内所有未获预约车辆立即施加制动。在相邻路口中，这可能让仍占用前一个路口的车辆为了下一个路口提前停下。新的规则保留提前预约，但只在速度相关停车距离内执行路口制动：区域半径 + 半车长 + 2米余量 + 一秒车程 + 按1.4米/秒²估算的制动距离。

路口实际占用检查、物理碰撞、近距离避障和外部控制边界保留。没有删除对象、移动实体或关闭碰撞；这不是完整交通信号优化，也不保证消除所有相互等待。专项测试覆盖前路口尚未驶出时不被远端预约提前制动，以及接近被占路口时仍须停车。

## 复现与边界

```bash
python -m unittest discover -s tests -v
python scripts/validate_journey_traffic.py --out outputs/stall-new --cars 96 --seconds 180 --seed 0 --mixed
python scripts/check_traffic_diagnostics.py --url http://127.0.0.1:8093 --out outputs/diagnostics-new
```

浏览器检查默认使用 `/usr/bin/chromium`，其他系统通过 `--chromium` 指定。原生检查每30仿真秒保存 `progress.json`，最终保存 `report.json`，包含等待关系、行人状态、实例身份、运动数和物理连续性检查。原脚本的 `passed` 表示碰撞/身份/分布等既有检查通过，不表示长期畅通；必须另看末段运动数、停车时长、循环等待和持续行程吞吐。

所有等待图、全场计数和路口预约均为围观调试信息，不加入 `vehicle_perception` 或 Planning 输入。当前观测仍按原白名单输出，不包含未来路线、事件时刻或全场等待图。不同交通规则的本轮对照用于修复背景交通，不是“只改变地图输入”的阶段五规划实验。

宽恒云选择与资源核验见 [云平台说明](kuanheng_cloud.md)。GPU不能自动消除交通规则的循环等待。

## 本轮量化结果

96车/16人、seed=0、混合事件180仿真秒，同一初始配置；只调整背景交通路口制动规则。

| 指标 | 原规则 | 修复规则 |
| --- | ---: | ---: |
| 完成行程 | 47 | 58 |
| 结束时运动车辆 | 10 | 28 |
| 结束时循环等待组 | 5 | 0 |
| 停车≥30秒车辆 | 66 | 37 |
| 最后30秒同实例净位移不足1米 | 68 | 52 |
| 记录碰撞 | 0 | 0 |

[保存的证据](../demo/simulation/validation/stall-diagnostics.json)包含各30秒采样、末帧等待关系和额外60秒诊断。修复版各采样未检出循环等待，仍有排队和跟踪/物理运动问题，不能宣称无限持续畅通。P12/P22在60秒仍有非零控制目标和较小横向误差却未前进，实际力/接触原因未确定；界面明确标注待核查。行人5物理受阻未修复。只验证本种子和该时长，不外推所有密度与时长。
